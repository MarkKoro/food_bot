# Подтверждение показанной цели Food

Решение D01: пользователь сохраняет именно показанные КБЖУ. Прежний HTTP baseline показал 2600 ккал при весе 70 кг, затем после параллельной правки до 100 кг старое подтверждение сохраняло не показанные 3075 ккал. Просмотр, переход, заполнение профиля и расчёт цели не записывают цель.

## Контракт владельца

`POST /api/progressor/profile/plan` с `apply:false` использует обычную проверенную личность Food. При успешном детерминированном расчёте Food сохраняет непрозрачный случайный `preview_id`, Telegram id владельца, точные серверные targets/результат, версию собственного профиля и цели, режим `use_shared` и hash использованного профиля/происхождения/конфликтов. Ответ содержит `preview_expires_at`. Клиентские targets и user_id не определяют сохраняемую цель. ИИ и платёжные провайдеры не вызываются.

Неприменённый preview действует 600 секунд. Это ограничение проекта, а не доказанный оптимальный срок чтения. `apply:true` требует тот же owner-bound `preview_id` и режим. Food сначала проверяет наличие/срок/владельца и возвращает уже применённый receipt без повторного чтения общего профиля. Для нового применения собственный snapshot и доступный общий профиль читаются до write transaction. Общий профиль поступает только через прежний проверенный Core endpoint с его правилами доступа, свежести и согласия; другой домен и его база напрямую не читаются.

Новый интерфейс подтверждает цель только через `POST /api/progressor/profile/plan/confirm` с `apply:true`. Это отдельный маршрут к тому же owner handler, без второго writer. При откате сервера старый API возвращает404 и ничего не записывает; UI предлагает обновить экран и не пробует прежний путь. Одна проверка capability перед запросом не закрыла бы смену версии между проверкой и записью. Прежний `/profile/plan` на новом API для совместимости также требует preview при `apply:true`; старый клиент без token получает409. Не добавлять автоматический fallback с нового confirm на legacy writer.

В короткой `BEGIN IMMEDIATE` транзакции Food повторно сравнивает локальную версию, hash контекста и полный серверный результат с сохранённым preview. Затем сохраняет точные targets и receipt одной транзакцией. Сбой записи receipt откатывает и цель. Native writers остаются независимыми: additive triggers увеличивают отдельные ревизии goals и progressor_food_profile при insert/update/delete, включая изменение с возвратом к прежним значениям и delete/recreate. Отсутствующая цель также входит в версию. Повтор запроса не создаёт ещё одну ревизию цели и не заменяет более позднюю native цель.

При изменении профиля, цели, использованного общего контекста/происхождения, режима, истёкшем или чужом/отсутствующем preview сервер возвращает 409 и предлагает новый расчёт. Недоступный Core при `use_shared:true` даёт 503 до записи цели; заполненный собственный профиль можно рассчитывать с `use_shared:false` независимо от Core. Core не вызывается внутри write transaction. Проверка общего контекста отражает последний успешный ответ Core перед записью; атомарной транзакции между независимыми базами нет.

Receipt содержит собственные показанные targets, `saved`, `duplicate` и `current_goal_matches`; старые shared provenance/profile не возвращаются. При более поздней правке цели повтор сообщает, что текущая цель отличается, и сохраняет последнее значение. После истечения срока хранения или удаления receipt старый token отклоняется; повторное применение под ним не создаётся.

## Интерфейс и хранение

Любое редактирование профиля или переключение общего профиля убирает подтверждение и требует новый расчёт. Ответ старого save не затирает более новый ввод. Поздний preview не восстанавливает кнопку после редактирования; поздний ответ apply не скрывает более новый preview. Ошибка ответа apply, кроме конфликта 409, сохраняет token для явного повтора. Одновременно выполняется только один save/calculate профиля; поля остаются доступны для новых правок. Если навигация открыла блок настроек до загрузки его скрипта, он загружает только собственные настройки, без расчёта/применения.

На владельца хранится не более восьми preview/receipt. При создании нового preview дополнительно удаляются до 256 записей старше 24 часов через индекс `(created_at,token)`; отдельного scheduled purge/worker нет. Проверка чтения независимо от физической уборки отклоняет записи старше 24 часов. Раннее вытеснение из восьми требует нового расчёта. `purge_user` удаляет собственные previews и обе таблицы ревизий вместе с профилем/целью; финансовая история и прочие данные сохраняют прежний контракт.

Миграция additive и выполняется прежним `db.create_tables`. Новые таблицы/индексы/триггеры нужно оставить при откате кода; живую базу не заменять. Версии локальны Food и не меняют канонические shared helpers или текущую семантику событий Core.

## Проверка

`tests/test_goal_preview.py` проверяет профиль/цель CAS и ABA, delete/recreate, отсутствующую цель, владельца/token/режим/TTL, повтор после потери ответа, две параллельные отправки, атомарный rollback receipt, cap8 и уборку batch256 с сохранением свежего чужого receipt.

`tests/test_growth.py` проверяет реальный owner API и временную SQLite: разделение preview/apply, подмену targets/user_id, параллельные правки, изменение/отзыв общего профиля, отказ Core, отсутствие write lock при shared recheck, повтор applied shared preview без нового доступа к Core и очистку новых записей владельца.

`tests/goal-preview-ui.test.cjs` использует реальную разметку блока и его скрипт в изолированном браузере с перехваченными ответами. Проверяются открытие до загрузки скрипта, правки во время save/preview, shared toggle, поздние success/409 apply и повтор с тем же token после ошибки. Отдельная смена backend после preview доказывает404 без fallback к старому writer, понятную ошибку и безопасный повтор после восстановления новой версии. Это браузерная эмуляция, не проверка физического Telegram/iPhone. Полная Linux/browser проверка и production rollout фиксируются отдельно в общем журнале поставки.
